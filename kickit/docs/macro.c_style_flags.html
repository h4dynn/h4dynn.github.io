Define traditional C-style flags in Rust fashion

This implementation is incredibly similar to the bitflags crate. Instead, here we represent single flags in an enum to be idiomatic, and a struct for concatenated flags.

§Motivation & comparisons

External crates such as nix have macros like libc_bitflags (private) for these C-style flags. For nix, this uses constant values defined under a zero-sized structure. This works very well for FFI, however, we can also represent these flags as an enum, and a structure of concatenated flags.

Representing like this allows for more of an idiomatic, Rust-like definition whilst retaining C compatibility.

§Example

c_style_flags! {
  #[repr(u8)]
  pub enum Emotion
  {
    Happy = 20,
    Sad = 1,
    Angry = 100
  }

  // Dereferences to u8
  pub struct Emotions([Emotion] as u8);
}

macro_rules! emotions
{
  [$($e: tt),*] =>
  {
    // Helper macro is provided 
    c_style_flags_construct!(<Emotions>::from([$($e),*]: [Emotion] as u8))
  };
}

fn main()
{
  // Sad (1) and Angry (100) are concatenated with bitwise OR operator
  let sad_and_angry = emotions![Sad, Angry];
  let bittersweet = emotions![Happy, Sad];
  let everything = emotions![Happy, Sad, Angry];

  // 100 | 1 = 101
  assert_eq!(*sad_and_angry, 101);
  // 20 | 1 = 21
  assert_eq!(*bittersweet, 21);
  // 20 | 1 | 100 = 117
  assert_eq!(*everything, 117);
}

You can see that having one unified number instead of multiple elements in an array can be a more efficient way to represent flags.

This is used for interopability with libc libraries (nix).

§Limitations

This macro does not implement parsing each flag individually after a Flags value has been constructed. This is because the types defined by this macro are used for libc libraries, where they are provided as arguments, so libc does the interpreting for us.
